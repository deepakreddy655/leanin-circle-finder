# Technical design — Circle Finder

**The product decision.** A recommendation is useful only if a member can act on it. I put **eligibility before relevance**: exclude existing memberships, unlisted Circles, full Circles, and inactive Circles (last activity over 45 days ago, or no posts and fewer than five chats in the last 30 days). A request-to-join Circle can appear, but the reason must say that joining requires approval.

**Ranking.** The strongest signal is a Circle's primary topic matching a member's **stated** interest (+75). A primary topic from an existing membership is a weaker signal (+18); overlapping tags are weaker still (+4 each, capped at +8) because some tags are noisy. Bounded activity, recent post engagement, recency, capacity, and open enrollment help order otherwise plausible options. Virtual/hybrid formats get a small accessibility preference because the dataset has no Circle locations. Scores are ranking heuristics, not probabilities. A cold-start member gets a deliberately broad starting shelf (leadership, confidence, mentorship, networking, communication) rather than an invented personal profile. After ranking, I keep at most one Circle per primary topic so near-duplicates don't crowd out other options.

**Explanations.** Each result says *why this topic*, whether the community is active, its format, and how to join. The wording distinguishes direct interests from weaker tag matches. I don't infer parenting status, location compatibility, or personal similarity from profile fields. This matters for a product intended to help members feel understood rather than stereotyped.

**Implementation.** FastAPI exposes `GET /recommendations/{user_id}`; SQLite stores normalized users, topics, interests, Circles, tags, memberships, and activity. The importer keeps the original synthetic JSON unchanged. A deterministic snapshot clock uses the latest supplied activity timestamp, so the same fixture won't become "inactive" as real time passes. At 40 Circles, simple on-request scoring is easier to inspect than introducing a recommendation service or vector database.

**Validation and limits.** Automated tests cover all 100 users, the four seeded cases, HTTP errors, integrity constraints, full/inactive changes, popularity outliers, and honest explanations. The main tradeoff is hand-tuned weights without user outcome data. A one-per-topic cap may hide a second excellent Circle. I also can't assess in-person travel feasibility because Circle locations are missing.

**For production.** Add authentication, real-time capacity checks, current activity aggregates, pagination, caching, observability, and PostgreSQL migrations. Gather opt-in member preferences and measure joins, sustained participation, and explanation usefulness before learning weights or A/B testing ranking changes. Review fairness and privacy impacts with members.
